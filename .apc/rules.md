## 规则与已知死路

- [ ] R1: 全屏主窗口保持原生层级提交，严禁引入 Web 视图。
  - **范围**：窗口与渲染
  - **证据**：Web 渲染管线内存消耗过大（>100MB），且跨进程 Surface 在隐藏再显示时容易产生撕裂与黑帧。
  - **规则**：主界面使用 GTK 4 原生控件与 RenderNode 渲染，Wayland 下通过 `gtk4-layer-shell` 直接以 OVERLAY 层级提交。

- [ ] R2: 物理按键监听必须由独立 evdev 线程拥有，禁止主循环休眠轮询。
  - **范围**：输入与按键
  - **证据**：外部应用拖拽时占用 Pointer Grab，合成器会吞掉普通快捷键，只有内核 evdev 能保证 100% 捕获硬件电平。
  - **规则**：打开 `/dev/input/event*` 阻塞读取 `EV_KEY`，长短按状态由微秒级时间戳判定，通过非阻塞 Channel 向 UI 线程投递。

- [ ] R3: 拖拽会话在拖出期间必须通过透明代理锚点保持 Surface 存活。
  - **范围**：拖拽交互
  - **证据**：Wayland 合成器在拖出源 Surface 隐藏或注销（Unmap）时会立即强制终止当前的 DnD 会话。
  - **规则**：向外部拖出中转项时，不隐藏主窗口，而是将其背景与卡片设为完全透明，待收到拖拽完成回调后再彻底隐藏。

- [ ] R4: 中转站只保存文件系统绝对路径引用，严禁擅自修改原文件。
  - **范围**：中转站数据
  - **证据**：擅自移动用户原文件会导致其他应用无法定位路径，甚至引发数据丢失。
  - **规则**：Stage 永远仅保存文件的标准绝对路径、MIME 类型、大小与 mtime，文件本身的物理生命周期由用户及原应用管理。

- [ ] R5: SQLite 必须采用 WAL 模式并由独立 Worker 独占写事务。
  - **范围**：存储与并发
  - **证据**：UI 线程同步写磁盘会造成卡顿，多连接写竞争会导致 database is locked。
  - **规则**：强行设置 `PRAGMA journal_mode = WAL;`，写操作通过有界 Channel 投递给单一 Storage Worker 串行执行。

- [ ] R6: 每次呼出必须严格绑定 GenerationId 代次，旧代异步结果一律丢弃。
  - **范围**：生命周期
  - **证据**：高频连续按键或快速拖放可能导致前一轮的异步回调（如缩略图就绪、隐藏超时）错误应用在当前新会话上。
  - **规则**：呼出时单调递增生成 `GenerationId`，UI 与 Worker 处理的所有请求均校验代次，旧代结果直接丢弃。

- [ ] R7: 虚拟键盘注入必须在浮层完全隐藏且失焦确认后执行。
  - **范围**：输入与注入
  - **证据**：若在工作台尚未交还前台焦点前就注入按键，Ctrl+V 会直接投递给工作台自身导致无效或触发内部快捷键。
  - **规则**：直接粘贴时，必须先将浮层 Unmap，确保原窗口重新获得活动前台焦点后，再向 `/dev/uinput` 发送按键事件。

- [ ] R8: 列表必须采用视口回收虚拟化控件，严禁无界创建 Widget 节点。
  - **范围**：视图与性能
  - **证据**：启动项、中转站历史、剪贴板累积上千条时，全量创建 GTK Widget 会导致常驻内存暴增（>200MB）且引发滚动严重掉帧。
  - **规则**：三大区域必须基于 `GtkListView` / `GtkGridView` 搭配 `GtkSignalListItemFactory` 与 `GListStore`，仅为当前可视视口实例化卡片 Widget，实现海量条目下内存恒定与流畅渲染。

- [ ] R9: 启动台与中转站卡片高度必须遵循显示区域整除算法，规避底部截断。
  - **范围**：布局与渲染
  - **证据**：传统固定像素高度在不同分辨率或非整除视口高度下，会导致最底部一行卡片被切断一半，造成视觉残缺。
  - **规则**：启动台与中转站共用高度动态适配算法，动态计算行高使得默认展示区域刚好容纳完整 $N$ 行，杜绝局部截断。

- [ ] R10: 浮层关闭与消费必须触发原子焦点返还，保障原应用输入上下文不丢失。
  - **范围**：焦点与交互
  - **证据**：用户呼出工作台常在特定编辑框或终端上下文中进行，关闭若未精确将前台激活权交还给原窗口，会导致后续敲击或直接粘贴丢失目标。
  - **规则**：呼出时暂存原活动窗口上下文，支持按 Esc、再次按快捷键或失焦（点击外部/任务栏）自动关闭；关闭瞬间完成焦点归还，失焦生命周期与消费时序严格因果同步。

- [ ] R11: 坚决杜绝直接复用 Workbench-APP 遗留代码与基于 sleep 的时序规避。
  - **范围**：架构纪律
  - **证据**：Workbench-APP 虽在功能与前端形态上验证成熟，但在技术架构上是由于多进程 Web 栈与异步时序失控导致性能低下与 sleep 泛滥的反面教材。
  - **规则**：仅将 Workbench 作为交互范式与功能清单参考，任何代码实现必须基于纯原生 Rust 与 Linux 系统协议重写，严禁直接照搬或引入其基于 sleep 的竞态规避逻辑。

- [ ] R12: GNOME Wayland 下 Xwayland 无法感知 Dock 空白处物理点击，严禁指针停驻猜想。
  - **范围**：窗口管理与输入隔离
  - **证据**：Ubuntu Dock 为 Mutter 内部的 Clutter actor（Chrome 层级），位于 X11 工作区外部。在 Wayland 隔离模型下，当光标处于 Dock 区域时 Mutter 不会向 Xwayland 派发指针与按键事件；点击空白处不触发窗口激活或焦点迁移（`_NET_ACTIVE_WINDOW` 与 `is_active` 均保持不变）。XInput2、`query_pointer` 均收不到事件。依赖光标坐标或停留时间（如 200ms）在用户正常移动或晃动鼠标时极易误伤，且自动化测试注入（`warp_pointer`）会产生虚假通过日志。
  - **规则**：严禁在 UI 轮询中通过光标坐标停驻时间猜想物理“点击”；要么依赖真实焦点迁移事件（Alt+Tab、其他应用激活、Super键系统概览），要么在具备 `/dev/input` 权限时由 `evdev` 直接读取硬件级输入流。

- [ ] R13: Wayland 坐标钳位与触控板轻击 (Tap) 状态机规约。
  - **范围**：输入感知与窗口隔离
  - **证据**：在 Wayland 环境下，光标移入 Ubuntu Dock (`x < 132`) 时，Xwayland 根窗口 `query_pointer` 坐标常被 Mutter 钳位在边界（`x=132`），导致 `x < wa.x` 几何判定失效；同时笔记本触控板轻击（Tap）由内核派发 `BTN_TOUCH` (330)，而非实体鼠标按键 `BTN_LEFT` (272)。若仅校验 `x < wa.x` 或仅监听 `BTN_LEFT`，会导致 Dock 空白处物理点击或轻击无法被感知。
  - **规则**：
    1. 窗口层级反向排除校验：外部点击判定统一采用 `is_outside = geom_outside || (vok_xid != 0 && child != vok_xid)`。由于 Vok 为 Xwayland 顶层窗口（XID: `0x1800004`），光标处于 Dock 时 Xwayland 的 child 为 0 或非 Vok 窗口，直接突破坐标钳位限制；
    2. 触控板轻击状态机追踪：`EvdevMouseWatcher` 必须监听 `BTN_TOUCH`，并在按下至抬起时间 < 250ms 时将其识别为物理 Tap，与物理按键（`BTN_LEFT/RIGHT/MIDDLE/SIDE/EXTRA`）同等触发外置点击退让；
    3. 日志因果性透明：严禁将切换应用/呼出终端时触发的普通 `Focus-Out` 误认为是点击 Dock 隐退，日志需明确记录是【内核硬件物理输入 (evdev)】还是【窗口前台焦点转移 (Focus-Out)】。
